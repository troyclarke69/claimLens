Fine-tuning a vision-language model for a regulated domain

Evidence-cited extraction from insurance claim documents

ClaimLens reads a scanned claim form or invoice and returns structured fields in which every value carries its evidence: the text it read and the box on the page it read it from. I fine-tuned Qwen2.5-VL-3B with supervised fine-tuning (SFT) and reinforcement learning (GRPO) on a free GPU, and measured what each actually contributed.

What I found

  1. Prompting has limits. A better prompt took valid JSON from 50% to 100%, but the base model still copied the invoice number into a missing claim number on every such invoice. Labelled examples removed it.
  2. SFT fixed behaviour, not perception. Grounding and hallucinations improved dramatically, but single-character misreads of long IDs barely moved. The vision encoder was frozen.
  3. Held-out layouts exposed shortcut learning. The model had partly learned label wording: under "Our reference", claim-number misses nearly doubled. Randomised layouts fixed most of it.
  4. With a control run, RL became a trade-off. GRPO cut hallucinations further but missed more; SFT on the same documents beat it on almost everything else. RL moved the caution/coverage balance, which is what its cost-weighted reward encoded.
  5. The fairness test found a robustness bug, not bias. Name-induced changes were unstable digit reads, not a consistent disadvantage for any group.

How it's built

Synthetic data

Claim forms and invoices with exact labels, scan noise and deliberate traps. Name-swapped fairness sets and held-out layouts.

Evaluation harness

Accuracy, grounding (IoU ≥ 0.5), hallucination, misses and an error taxonomy. Versioned; the same code is the RL reward.

SFT + GRPO

LoRA on the language layers. GRPO with a reward where a wrong value costs twice an honest “not found”.

Audit & release

Hash-chained log of every prediction, fingerprinted adapters, a registry with a release gate.

Service

FastAPI POST /v1/extract returns fields, human-review flags and an audit receipt. Dockerised.

Limitations

All data is synthetic and single-page, from a small number of templates; 100 documents per evaluation set; single runs. Name groups are a crude proxy for audit-style testing, not demographics. A production system would need real, consented data and legal and domain review of the fairness criteria.
